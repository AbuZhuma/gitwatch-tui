# ТЗ: gitwatch-tui

## 1. Общая концепция

**Название (рабочее):** `gitwatch-tui` (имя на crates.io нужно проверить на занятость перед стартом)

**Одна строка:** Терминальный live-дашборд, который показывает все открытые PR пользователя по всем репозиториям и сам подсвечивает, какие требуют действия прямо сейчас.

**Питч для README:**
> gitwatch lives in your terminal and taps you on the shoulder the moment something across your repos needs you — no more refreshing GitHub in 15 tabs.

**Целевая аудитория:** разработчик в компании или организации с 5+ активными репозиториями (микросервисы, монорепо-сплит), который одновременно выступает автором и ревьюером PR.

**Проблема, которую решает:** GitHub не даёт нормального cross-repo view по PR. Notifications — это неструктурированный шум. Разработчику приходится вручную держать в голове или открывать вкладками 5-10 репозиториев, чтобы не пропустить упавший CI, новый review-комментарий или готовый к мержу PR.

**Ключевая дифференциация (то, чего нет у конкурентов вроде `gh dash`):**
- Не просто список PR, а **приоритизация по срочности действия**, а не по дате/репозиторию
- **Live-режим** — постоянно открытое приложение (живёт в tmux-панели), с автообновлением и нотификациями о новых событиях, а не разовый снапшот
- Read-only по дизайну — низкий порог доверия при установке

## 2. Scope v1 (MVP)

### Входит в scope:
1. Аутентификация через уже существующий `gh auth token` (никакого отдельного onboarding с PAT)
2. Получение всех открытых PR, где пользователь — автор, по всем репозиториям, к которым у него есть доступ (с возможностью ограничить конкретной организацией/списком репо через конфиг)
3. Классификация PR на три уровня срочности:
   - 🔴 **Требует действия сейчас**: CI failed на PR пользователя; PR approved всеми required reviewers и не имеет конфликтов (готов к мержу); пользователя явно упомянули (@mention) в новом комментарии
   - 🟡 **Скоро потребует**: PR без ревью более N дней (по умолчанию 2, настраивается); есть конфликт с base-веткой; частичный approve (не все required reviewers одобрили)
   - ⚪ **Фоновое**: всё остальное (PR, где пользователь просто упомянут как watcher/reviewer без открытых вопросов)
4. TUI-таблица: репозиторий, заголовок PR, статус CI, категория срочности, время последнего изменения
5. Live-режим: поллинг каждые 30-60 сек (настраивается), через GraphQL-батчинг запросов (один запрос на все репо разом, не N отдельных REST-вызовов)
6. Визуальная индикация новых событий — обязательная часть, работает всегда, без внешних зависимостей
7. Системные desktop-нотификации — опциональная фича (`--notify` / `notifications = true` в конфиге), с тихим фолбэком, если notification daemon недоступен (SSH-сессия, headless Linux, Docker)
8. Навигация клавиатурой (стрелки/vim-keys j/k), Enter — открыть PR в браузере (`open`/`xdg-open`/`start` в зависимости от ОС)
9. Базовый конфиг-файл (`~/.config/gitwatch/config.toml`): интервал поллинга, список репо/организаций для отслеживания, пороги для жёлтой категории, вкл/выкл нотификаций

### Не входит в scope v1 (осознанно отложено):
- Любые действия с GitHub напрямую из TUI (approve, merge, comment, re-run CI) — всё через "открыть в браузере"
- Мониторинг issues и discussions — только PR, для фокуса продукта
- Облачный бэкенд или синхронизация между машинами — всё работает локально, токен не покидает машину
- Полностью кастомизируемые правила приоритизации (только пороги по дням и список включённых правил, без произвольной DSL) — это в v2
- Поддержка GitLab/Bitbucket — только GitHub в v1

## 3. Технический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Язык | **Rust** (edition 2021) | Производительность, маленький бинарник, отсутствие рантайм-зависимостей при дистрибуции |
| TUI-фреймворк | **ratatui** | Активно поддерживаемый форк tui-rs, богатый набор виджетов (таблицы, гейджи, списки) |
| Terminal backend | **crossterm** | Кроссплатформенность (Linux/macOS/Windows) "из коробки" |
| Async runtime | **tokio** | Нужен для параллельных/неблокирующих запросов к GitHub API во время отрисовки UI |
| GitHub API клиент | **octocrab** (или сырой `reqwest` + `graphql_client` для GraphQL-запросов) | Типизированный доступ к REST; для батчинга через GraphQL может понадобиться отдельный слой поверх `reqwest` |
| HTTP-клиент (если нужен отдельно от octocrab) | **reqwest** | Стандарт де-факто в экосистеме |
| Сериализация | **serde** + **serde_json** / **toml** | Для конфигов и парсинга ответов API |
| Системные нотификации | **notify-rust** | Кроссплатформенный, с graceful degradation при отсутствии notification daemon |
| Получение auth-токена | вызов `gh auth token` через `std::process::Command` | Не просим пользователя городить свой PAT — резко снижает порог входа |
| Открытие ссылок в браузере | **open** (crate) | Кроссплатформенная обёртка над `xdg-open`/`open`/`start` |
| Логирование | **tracing** + **tracing-subscriber** | Для дебага, пишется в файл, не мешает TUI-выводу |
| CLI-аргументы | **clap** (derive-макросы) | Стандарт для флагов типа `--notify`, `--interval`, `--config` |
| Сборка релизов | **cargo-dist** или ручной GitHub Actions matrix-build | Автоматическая сборка бинарников под Linux/macOS/Windows на каждый релиз |

## 5. Нефункциональные требования

- **Rate limit GitHub API:** не более 1 батч-запроса (GraphQL) за интервал поллинга на весь набор отслеживаемых репозиториев — не N отдельных REST-вызовов на каждый репозиторий
- **Потребление ресурсов:** приложение должно быть "тихим соседом" в фоне — минимальная нагрузка на CPU между поллингами, не дёргаться визуально при каждом обновлении без реальных изменений данных
- **Кроссплатформенность:** обязательная поддержка Linux, macOS, Windows — как минимум сборка и базовая работа TUI и open-in-browser на всех трёх
- **Установка в одну команду:** `cargo install gitwatch-tui` или скачивание бинарника из GitHub Releases — без дополнительных шагов настройки, кроме уже залогиненного `gh auth login`
- **Безопасность:** токен не сохраняется и не логируется приложением, используется только в памяти на время сессии (берётся каждый раз через `gh auth token` или кешируется в памяти процесса)

## 6. Возможные точки роста (v2+, не реализуется сейчас)

- Конфигурируемые правила приоритизации через `gitwatch.toml` (произвольные условия, не только пороги)
- Action-режим: approve / merge / comment / re-run CI прямо из TUI
- Мониторинг issues и discussions
- Поддержка других платформ (GitLab, Bitbucket)
- Пресеты правил, которые пользователи могут публиковать и делиться (потенциальный источник community-контрибуций)

## 7. Критерии успеха запуска

- Работающий бинарник, который можно поставить и запустить за < 2 минуты от `git clone` до первого запуска
- README с GIF-демонстрацией live-режима в действии
- Публикация в формате "Show HN" / Reddit r/rust / r/programming с понятным описанием боли и решения
- Минимум 3-5 захардкоженных, но понятных и объяснимых правил классификации — никакой "магии", которую сложно объяснить в одном абзаце
